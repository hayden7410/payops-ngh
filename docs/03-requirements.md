# PayOps AI — Requirements Specification

## 1. Purpose

This document defines the functional and non-functional requirements for PayOps AI.

---

# 2. Authentication Requirements

## FR-01 — Login

The system shall authenticate users before allowing access to payment operations.

## FR-02 — Logout

The system shall allow authenticated users to terminate their session.

## FR-03 — Protected Resources

The backend shall reject unauthorized access to protected application resources.

---

# 3. Payment Data Requirements

## FR-04 — Retrieve Transactions

The system shall retrieve relevant PayPal Sandbox transaction information.

## FR-05 — Retrieve Invoices

The system shall retrieve PayPal invoice information.

## FR-06 — Retrieve Payment Summary

The system shall calculate payment summaries from trusted backend information.

---

# 4. Payment Operations Intelligence

## FR-07 — Detect Unpaid Invoices

The system shall identify invoices that remain unpaid.

## FR-08 — Detect Overdue Invoices

The system shall identify unpaid invoices whose due date has passed.

The number of days overdue shall be calculated by backend logic.

---

## FR-09 — Reconcile Payments Against Invoices

The system shall compare relevant payment information against invoice information.

Possible reconciliation results include:

```text
MATCHED
UNPAID
PARTIALLY_PAID
OVERPAID
UNMATCHED
```

---

## FR-10 — Detect Partial Payments

The system shall identify cases where the received amount is lower than the expected invoice amount.

Example:

```text
Invoice amount: $1,200
Received: $800
Remaining: $400

Status:
PARTIALLY_PAID
```

---

## FR-11 — Detect Possible Duplicate Activity

Where sufficient data is available, the system should identify potentially duplicated payment activity.

This is a P1 requirement.

---

## FR-12 — Calculate Issue Priority

The system shall calculate an operational priority for identified payment issues.

Priority factors may include:

- affected amount;
- days overdue;
- percentage of total outstanding balance;
- repeated failures;
- reconciliation status.

Possible values:

```text
LOW
MEDIUM
HIGH
```

Priority calculations should be deterministic where possible.

---

## FR-13 — Generate Operations Summary

The system shall generate a structured summary of payment issues requiring attention.

The summary may include:

- issue count;
- total value affected;
- highest-priority issue;
- overdue amount;
- partial-payment amount.

---

# 5. AI Requirements

## FR-14 — Natural-Language Interaction

The user shall be able to communicate with Gemini 2.5 Flash-Lite using natural language.

---

## FR-15 — AI Tool Selection

Gemini shall select only predefined backend tools.

The model shall not have arbitrary PayPal, database, HTTP, or system access.

---

## FR-16 — Explain Operational Findings

Gemini shall explain why an operational issue was identified.

Example:

> “This invoice is high priority because it is 18 days overdue and represents 44% of your total overdue balance.”

---

## FR-17 — Recommend Next Actions

Gemini shall recommend reasonable next steps based on verified findings.

Recommendations are advisory and do not constitute financial authorization.

---

## FR-18 — Answer Priority Questions

The user shall be able to ask:

> “What should I handle first?”

The system shall respond using priority results generated by backend services.

---

## FR-19 — Support Investigation

The user shall be able to investigate identified issues conversationally.

Examples:

> “Why is this high priority?”

> “How much is still outstanding?”

> “Which customer has the largest unpaid balance?”

---

## FR-20 — Structured AI Responses

The application shall support structured responses such as:

```text
TEXT
METRIC
TABLE
ISSUE_LIST
RECOMMENDATION
ACTION_PREVIEW
```

---

# 6. Financial Action Requirements

## FR-21 — Prepare Invoice

The user shall be able to request invoice preparation through natural language.

## FR-22 — Identify Missing Fields

The system shall request required invoice information that is missing.

## FR-23 — Generate Action Preview

The system shall display the complete proposed action before execution.

## FR-24 — Require Confirmation

Financial write operations shall require explicit user confirmation.

## FR-25 — Create PayPal Invoice

After confirmation, the backend shall create the invoice through PayPal Sandbox.

## FR-26 — Prevent Duplicate Execution

Repeated action submissions should not unintentionally create duplicate financial operations.

---

# 7. Operations Queue Requirements

## FR-27 — View Prioritized Issues

The merchant shall be able to view identified operational issues ordered by priority.

Each issue should contain:

- issue type;
- priority;
- amount affected;
- relevant resource;
- reason;
- recommended next action.

---

# 8. Audit Requirements

## FR-28 — Record Financial Actions

The system should record important financial action events.

Examples:

```text
ACTION_PREPARED
ACTION_CONFIRMED
ACTION_COMPLETED
ACTION_FAILED
ACTION_CANCELLED
```

---

# 9. Non-Functional Requirements

## NFR-01 — Security

Payment and authentication functionality must follow the controls defined in `05-security-design.md`.

## NFR-02 — Trusted Financial Data

Gemini must not generate authoritative financial facts.

## NFR-03 — Explainability

Operational findings should include the underlying reason they were classified or prioritized.

## NFR-04 — Human Authority

AI recommendations must not automatically trigger financial write operations.

## NFR-05 — Reliability

Critical calculations must be implemented in deterministic backend services where practical.

## NFR-06 — Performance

The user interface should provide loading feedback while external APIs or AI responses are being processed.

## NFR-07 — Error Handling

External service failures must not result in fabricated data.

## NFR-08 — Maintainability

AI, PayPal, intelligence, authentication, and persistence layers should remain modular.

## NFR-09 — Secret Management

Secrets must remain backend-only and excluded from the public repository.

## NFR-10 — AI Provider Abstraction

Gemini should be accessed behind an internal provider interface to reduce vendor coupling.

---

# 10. Priority Levels

### P0

Required for MVP.

### P1

Important if development time permits.

### P2

Optional/stretch capability.

---

# 11. Core Requirement Principle

The application must demonstrate:

```text
Financial Data
     ↓
Deterministic Analysis
     ↓
Operational Finding
     ↓
AI Explanation
     ↓
Recommendation
     ↓
Human Decision
     ↓
Financial Action
```

The AI should add reasoning and operational value rather than function only as a conversational search interface.
